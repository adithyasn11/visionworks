Team Brief · AD16

Turning office CCTV into a consented workforce analytics tool

VisionWorks reads an ordinary camera feed and answers questions facilities and people managers currently guess at: which parts of this office are actually being used, and how is a specific employee's day actually spending itself? It does this without ever saving footage, and it identifies a person only when that person has consented — everyone else is counted, never named.

01 — The problem

Cameras that only look backwards, and monitoring that only works blunt

Almost every office already has CCTV. But that footage is only ever watched after something goes wrong — a theft, an accident, a dispute. It is a recording device, not an information source. And the tools that do try to measure the workday — badge swipes, keystroke loggers, hours logged — measure presence or activity, not whether anyone actually got anything done.

Managers are making two different kinds of decisions blind. Facilities decisions: how many desks do we need, is that meeting room worth the lease. And people decisions: is this employee's time at their desk real focus or just stillness, is that unusual alert a genuine problem or a camera glitch. Today both get answered by gut feeling, a clipboard walkthrough once a quarter, or invasive tools that measure the wrong thing and damage trust the moment employees notice them.

Why the existing alternatives don't work

  • Dedicated occupancy sensors — desk sensors, door counters, badge readers. They cost money per unit, need installation and maintenance, and only tell you someone is present, never what they are doing.
  • Manual surveys and walkthroughs — accurate for one afternoon, then instantly stale. Doesn't scale past a single floor, and consumes staff time every time you want fresh numbers.
  • Keystroke and screen monitoring — invasive, provokes pushback the moment employees find out, and still misses real work done away from a keyboard: meetings, whiteboarding, reading.
  • Existing CCTV analytics products — most work by storing footage or running facial recognition on every frame. That is exactly what gets a project rejected by HR and legal, whether the goal is space planning or people analytics.
The gap we're filling: the hardware is already on the wall. What's missing is software that turns it into both occupancy data and, where an employee has explicitly agreed to it, individual desk-time data — in a way a company's legal team will actually sign off on.
02 — What we built

From pixels to two kinds of decisions

The system watches a video feed and produces the same four base numbers for everyone: how many people are present, what they're doing (sitting, standing, walking), which area of the floor they're in, and how long they stay there. That alone drives the anonymous, zone-level analytics.

For an employee who has explicitly consented, a second layer runs in parallel: appearance re-identification stitches that person's fragmented tracker IDs into one stable identity for the session, binds it to their name via the desk zone they're assigned to, and rolls the result into per-employee desk time, breaks, and away-from-desk counts. An employee who has not consented is never touched by this path — they flow through the anonymous pipeline exactly as before, and no row anywhere can name them.

Everything else in the product — the dashboards, the charts, the exported reports, the alerts — is built on those numbers. The critical design decision is what happens to the video itself: it is analysed frame by frame and then thrown away. Nothing is written to disk. What gets saved is a row of counts, and only a consenting employee's rows are ever attributable to them by name.

03 — Technology

What we used, and why we chose it

Every piece here was picked for a specific reason. Where a simpler option existed, the note says why we didn't take it.

The AI / computer vision layer

YOLOv8Finding people in a frame

A neural network that looks at an image and draws a box around every person it sees. We use the medium "pose" variant, which does something extra: instead of just a box, it returns 17 body points (shoulders, hips, knees, ankles). Those points are what make posture detection possible. Choosing the pose model meant we get detection and skeleton data in one pass on the graphics card instead of running two separate models.

ByteTrackFollowing the same person across frames

Detection alone is amnesiac — each frame it finds "a person", with no idea it's the same person as last frame. ByteTrack assigns an ID so we can measure how long someone stayed within one unbroken stretch. It has no appearance memory though: occlusion behind a monitor or colleague for ~30 frames resets the ID, which is exactly the gap the Re-ID layer below closes.

OSNet (torchreid)Recognising the same person after a lost track

A 512-dimensional appearance embedding, purpose-built for exactly the crop size (128×64) this pipeline already produces — smaller than what face recognition needs to work at all. When a track is lost and a new one appears, we compare embeddings; measured on real footage, a cosine similarity above 0.65 accepts 97.9% of true same-person matches while wrongly accepting only 5.7% of different people. Fused with a colour histogram and homography-based height, this stitches fragments back into one stable identity — without ever running face recognition on most cameras.

InsightFace (ArcFace + SCRFD)One-time, opt-in enrolment

Runs only on a camera explicitly marked as a door camera, and only to bind an identity to a named employee at enrolment — never continuously, and never on an ordinary area camera. An employee can withdraw consent at any time, which deletes their stored face embeddings outright.

ShapelyDeciding which zone a person is in

Once you've drawn a zone as a polygon, you need to ask "is this person's position inside that shape?" thousands of times a second. Shapely is a computational geometry library that answers that fast and correctly, including for irregular non-rectangular shapes — and it's also the strongest signal for binding an identity to the employee assigned to that desk.

OpenCVVideo handling + the privacy blur

Reads video files and camera streams, resizes frames for speed, and applies the Gaussian blur over the head region before any frame is sent to a browser. Also provides the homography maths that converts a tilted camera view into a top-down floorplan position.

PyTorch + CUDARunning the model fast

PyTorch is what YOLOv8 runs on; CUDA lets it run on an NVIDIA GPU rather than the CPU. Measured on our development machine: ~75 frames per second on GPU versus ~7 on CPU — a 10× difference, and the reason live processing is viable at all.

The backend

FastAPIThe Python server

The AI libraries are all Python, so the server handling them had to be Python too. FastAPI has native WebSocket support, which is essential here — we're pushing a processed video frame plus its data many times a second, and a normal request/response API can't do that.

WebSocketsLive two-way streaming

Keeps an open channel between browser and server. The server pushes annotated frames down; the browser sends controls up (pause, seek, toggle blur). Without this the live view would be impossible — you'd be reloading a page dozens of times a second.

SQLAlchemy + SQLiteLocal buffer for raw telemetry

The pipeline produces a result for every person on every frame — far too much to write straight to a cloud database. Raw readings land in a local file-based database first, get sampled (once every 5 seconds per person, plus immediately on any posture change), then rolled up two ways: anonymously by zone for everyone, and by named identity for consenting employees only — before either is pushed to the cloud.

reportlab + pandasGenerating exports

pandas assembles the numbers into a table for CSV export; reportlab builds the formatted PDF summary a facilities manager can forward to their director without editing it first.

The frontend

Next.js + ReactThe web application

React builds the interface; Next.js adds server-side rendering and Server Actions, which matter for security — permission checks run on the server where a user can't tamper with them, not in browser code they could edit.

Tailwind CSSStyling

Keeps styling consistent across ~90 files without a sprawling stylesheet, and made the light/dark theme a single set of variable swaps rather than two parallel designs.

Recharts + heatmap.jsCharts and the floorplan overlay

Recharts draws the occupancy and posture trend lines. heatmap.js renders the top-down density map showing where people cluster on the floor.

HTML CanvasDrawing boxes over live video

The bounding boxes, ID tags and posture labels you see over the video are drawn onto a canvas layered on the frame — fast enough to redraw every single frame without stuttering.

Data, accounts and security

SupabaseLogin + cloud database

Handles sign-up, passwords and Google sign-in so we never store a password ourselves. It's PostgreSQL underneath, which gives us the security model below. Using a managed service here let us spend our time on the CV pipeline rather than rebuilding authentication.

PostgreSQL + Row Level SecurityKeeping companies' data separate

This is the most important choice in the whole project. RLS enforces data isolation inside the database itself, not in our application code. Company A physically cannot read Company B's data even if we wrote a buggy query — the database refuses. That's what makes this safe to run as a shared service for multiple client companies.

PrismaDatabase schema management

Defines all 22 data models (organisations, cameras, zones, alerts, reports, audit logs, employees, consent records, identity events, per-employee day stats…) in one file, and tracks the 24 migrations that got the database to its current shape — so the schema is version-controlled alongside the code.

Why two databases? The local SQLite file absorbs the firehose of raw per-frame readings, which would overwhelm a cloud database and cost a fortune. Only the cleaned, summarised rows travel up to Postgres — anonymous per-minute zone rows for everyone, and per-employee day rows only where consent exists. It's the difference between shipping every frame and shipping a receipt.
The consent boundary, structurally: zone_minute_stats has no column that can hold a person, and it is never touched by identity code. Per-employee data lives in separate tables (employees, identity_events, employee_day_stats), gated on a consent record, with the strongest signal for naming someone — desk-zone assignment — reused from the zones a manager already draws. Revoking consent is a row delete, not a pipeline change.
04 — A closer look

How the system knows someone is sitting

This is the part people ask about most, so it's worth explaining plainly.

The pose model returns 17 points on each person's body. From those we compute the angle at the knee and the hip — the same way you'd judge it by eye. A standing person's leg is close to a straight line; a seated person's knee is bent near ninety degrees and their hips sit low relative to their shoulders.

Walking is separated from standing using movement speed: we track how far a person's position shifts between frames. Someone standing still at a desk and someone walking past look similar in a single frozen frame — motion over time is what distinguishes them.

Because a single frame can be misread (someone mid-stride, or partially hidden behind a desk), the result is passed through a 7-frame rolling majority vote: the posture reported is whichever one won across the last seven frames. This removes the flickering you'd otherwise get where a label rapidly alternates between two states.

Worth being honest about: this is a geometric rule-based classifier we designed, not a trained-and-benchmarked model. It behaves sensibly on our test footage, but we have not yet measured its accuracy against a hand-labelled dataset. That's the clearest next step for the project.
04b — A closer look

How the system knows who someone is — without face recognition

ByteTrack alone cannot answer "who is this" across a session, only "is this the same blob as last frame". Getting from a tracker fragment to a named, consenting employee takes three stages.

Stage one, re-identification. Every detection gets an appearance signature — an OSNet embedding, an HSV colour histogram split at the hips using the pose keypoints we already compute, and a height estimate from the homography. When a tracker ID is lost, typically from occlusion, and a new one appears, we compare its signature against a short-lived gallery of recently-lost identities. A cosine similarity above 0.65 — a threshold measured on our own footage, not assumed — reattaches it as the same person instead of minting a new identity.

Stage two, binding. An identity is bound to a named employee purely through the desk zone they're assigned to: whichever identity spends the majority of its time in that zone gets bound, with a confidence score equal to the fraction of time spent there. No biometrics are involved in this step at all.

Stage three, consent. None of the above writes a named row anywhere unless a consent record exists for that employee. Withdrawing consent deletes their enrolled face data outright, and their day forward flows through the anonymous pipeline exactly like everyone else's.

Worth being honest about: binding accuracy depends on the office having mostly fixed seating — it degrades in a hot-desking environment, and we say so rather than hide it. The stitch-threshold numbers above (97.9% correct accept, 5.7% false accept at 0.65 cosine) are measured on our own test footage in test_appearance.py, not a published benchmark, and are the clearest thing left to validate against a larger, hand-labelled dataset.
05 — The product

What each page does

The application has three distinct areas: the setup flow, the manager's workspace, and an internal console for whoever operates the service.

Getting started

Landing page
public

Explains the product to a visitor. Includes a dedicated security page describing the privacy design, because that's the first question a prospective customer asks.

Sign up / Log in
public

Email and password, or one-click Google sign-in. Existing invitations are matched automatically by email address, so an invited colleague just signs up normally and lands in the right company.

Onboarding
new users

Three steps: create the organisation (required), describe the site and its working hours (skippable), add a first camera (skippable). Only the first is mandatory — an evaluator can look around before committing to a full setup.

The manager's workspace

Overview
everyone

The home screen. Six headline numbers — people seen, activity level, zones in use, busiest zone, longest continuous sitting, last detection — plus a posture breakdown, an alerts feed and trend charts. Deliberately restrained: a number nobody acts on is clutter.

Live feed
manager +

Upload a recording or switch on a camera and watch the analysis happen in real time — boxes, IDs, posture labels, live zone counts, and a blurred head region on every person by default. Full playback controls for uploaded video.

Zones
manager +

Draw the areas you want measured directly onto a camera frame — click points to outline a desk, a meeting room, a corridor, then name it. These shapes are what occupancy, dwell time, and desk-based identity binding all get attributed to.

Employees
manager +

Add employees, assign each a desk zone, and manage consent and face enrolment. Nothing about a specific employee is ever tracked until a consent record exists for them here.

Team
manager +

Per-employee daily view for consenting employees only — desk time, breaks, away-from-desk counts — each figure shown alongside the confidence behind it, never presented as unqualified fact.

Camera topology
manager +

Declare which camera's exit plausibly leads to which camera's entry, and how long that walk should take. Used to sanity-check identity handoffs between cameras rather than trust appearance matching alone.

Reports
everyone

Export the selected date range as a CSV of raw numbers or a formatted PDF summary. Zone-level exports contain counts and postures, never a person; per-employee exports are only available to whoever's role permits individual data, and only for consenting employees.

Plan
admin only

Subscription tier, what it includes, and in-app upgrade. Hidden entirely from non-admins, since billing is a governance decision rather than an operational one.

Members
everyone reads

The team roster. Any member can see who their colleagues are; only an admin gets the invite form and the row controls to change roles, suspend or remove someone.

Organisation settings
admin only

Company name, timezone, data retention window, and account deletion — the controls that decide when data is destroyed.

The operator console

Platform admin
us, not customers

A separate console for running the service itself: every client organisation, their health status, suspend/restore, retention policy, operator access management, and an append-only audit log of every administrative action. Crucially, an operator here can see that a company is using the system but cannot read any company's actual occupancy data — that boundary is enforced by the database.

07 — The case for it

How a company would actually use this

Each number the system produces maps to a decision someone is currently making blind.

Right-sizing the office

If the data shows a meeting room sits empty 80% of the week while another is permanently booked, that's a concrete argument for converting one into desks — or not renewing that part of the lease. On a multi-year office lease, that single decision can outweigh the entire cost of running this system.

Understanding when, not just whether

Peak-hour data tells a facilities team when the building is actually full. That feeds cleaning schedules, reception staffing, HVAC timing, and flexible-hours policy — all currently set by assumption.

Wellbeing, measured at the zone level by default

By default the system flags zones with unusually long unbroken sitting time, never individuals — supporting an argument for standing desks or layout changes without singling anyone out, because the anonymous data physically cannot.

Per-employee visibility, only where it's been agreed to

For an employee who has consented, the same pipeline answers a different question: how much of their day was actually spent at their desk, how many times did they step away, and for how long. That is the number a manager currently has no honest way to get without a keystroke logger — and this gets it without one, attaching a confidence to every figure rather than presenting it as unqualified fact.

Why the privacy design is the commercial argument

Workplace monitoring products usually die in a legal review. Ours is built so the honest answer to "what do you store about our employees?" is: nothing that refers to a specific person, unless that person explicitly consented — and even then, nothing beyond what they consented to, for longer than the retention window allows. No footage on disk. No face recognition running continuously. That isn't a policy promise we're asking anyone to trust — the anonymous path and the consented path are structurally separate tables, and consent withdrawal is a row delete, not a request someone has to action.

The one-line pitch: companies already own the cameras. This turns them into a tool that shows which areas are wasted or overcrowded for everyone, and — only where an employee has agreed — how their own day actually breaks down, without ever running continuous face recognition or storing footage.
08 — Where we are

Current status and what's next

Working end to end

  • Full CV pipeline — detection, tracking, posture classification, zone attribution, dwell and activity scoring
  • Appearance re-identification stitching ByteTrack fragments into stable identities, with the 0.65 cosine threshold measured on real footage (97.9% correct accept, 5.7% false accept)
  • Seat-based identity-to-employee binding and a per-employee daily aggregator (desk time, chair exits, breaks, focus blocks)
  • Consent-gated face enrolment at door cameras, with consent withdrawal deleting stored embeddings
  • Live processing over WebSocket for uploaded video, browser webcam and server-attached camera
  • Head-region blurring applied by default before any frame reaches a browser
  • Zone drawing wired to real occupancy attribution, on both the anonymous and per-employee paths
  • Dashboard, trend charts, alerts, and CSV/PDF export reading real recorded data, including per-employee and team views
  • Accounts, Google sign-in, invitations, three-tier roles, multi-company data isolation
  • Platform operator console with audit logging
  • Camera-topology editor for declaring plausible walk times between cameras

Known gaps we're being upfront about

  • Accuracy is only partly measured. The re-identification threshold is benchmarked; posture classification and end-to-end identity-binding accuracy against a hand-labelled dataset are not. This is the top priority.
  • The agentic reasoning layer is not built yet. The plan calls for four agents — a Behaviour Interpreter that judges a day's pattern with a stated confidence, an Anomaly Investigator that distinguishes a real event from a sensor artefact before alerting, a Privacy Guardian that gates every individual-level query, and an Insights Narrator for weekly briefings. None of this exists in code today; the current per-employee numbers are aggregator output, not agent-reasoned output.
  • Cross-camera handoff is unvalidated. The topology editor exists, but matching an identity across two cameras and tuning the fusion weights on real handoff data has not been done.
  • Camera identity bridging. Linking a registered camera to a processing session currently relies on names matching exactly; this needs a proper picker in the interface so it can't be got wrong.
For anyone presenting this: the strongest thing about the project isn't any single model — it's that a complete path exists from a camera frame to a consented, confidence-scored per-employee figure, with the anonymous path staying anonymous by construction rather than by promise. Lead with that, and be upfront that the agentic reasoning layer is the next thing being built on top of it, not something already running.
